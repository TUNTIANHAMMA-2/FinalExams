# 答辩常见问答（预设）

> 先占位常见问题，填好交付物后补具体答案与数据。

**Q1：为什么用自己的项目而不是给定的参考项目？**
A：RhizoDelta 真实可运行、接口丰富，且我对业务最熟悉，能写出有依据的用例、对缺陷定位更准；同时它是标准 B/S + REST 系统，完全满足考查要求。

**Q2：你的测试范围怎么定的？为什么不测 AI 和 SSE？**
A：本轮核心聚焦认证授权、用户资料基础接口、图谱查询基础接口、登出与 token 吊销等可确定断言的同步 REST 行为；发帖关联、头像上传、关注/拉黑、治理流程已列为后续扩展；AI 质量、SSE 实时、异步重试这类非确定性强、超出课程周期，只在总结报告说明取舍。

**Q3：接口测试和功能测试有什么区别？你怎么做接口测试？**
A：功能测试从用户界面验证；接口测试用 Postman 直接对 `/api/**` 发请求，断言状态码、响应结构 `ApiResponse` 和业务字段，能更早、更精确地发现后端问题；用环境变量管理 token，用 Collection Runner 批量执行并导出报告。

**Q4：用了哪些用例设计方法？举例。**
A：等价类划分用于 username、password、token、refresh_token、分页参数、UUID；边界值用于空用户名、密码 8 位、负页码、UUID 格式；错误推测用于重复注册、伪造 token、缺字段、无 token 访问；场景法覆盖注册→登录→查询资料→刷新令牌→图谱查询→登出→旧 token 失效；因果图覆盖登录的账号存在性与密码正确性组合。

**Q5：发现了哪些典型缺陷？严重程度如何判定？**
A：发现 2 个低危缺陷：BUG-001 重复用户名注册实返 400，但 REST 语义上更适合 409 Conflict；BUG-002 在线状态接口 `last_active` 为字符串型 epoch，与其它时间字段格式不一致。严重程度按是否阻塞主流程、影响范围、是否有规避方案分为严重/很高/高/中/低，两项均不阻塞核心流程。

**Q6：怎么保证测试覆盖率/可信度？**
A：按模块需求编号组织用例，20 条已实测核心子集用例执行率 100%；接口用例覆盖正常、异常、鉴权、参数校验和状态迁移分支；测试用例表另补充 8 条等价类/边界值回归设计用例；缺陷全部登记并定级，未执行的发帖、关联、治理、SSE 已明确列为后续扩展或范围外。

**Q7：如果让你继续，下一步测什么？**
A：性能（JMeter 压测登录/查询接口）、UI 自动化（Selenium 回归）、SSE 与异步的一致性专项。
