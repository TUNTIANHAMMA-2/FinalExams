# 宿舍报修管理系统答辩准备说明

这份文档的作用是帮你答辩时讲清楚：这个项目做什么、为什么这样设计、每张图是什么意思、老师可能会问什么。表达尽量按“答辩时能直接说出来”的方式写，不追求很复杂的书面话。

## 一、项目一句话说明

我的项目是一个“宿舍报修管理系统”的分析与设计。它主要解决学生宿舍维修过程中报修不统一、进度不好查、派工没有记录、后勤统计麻烦这些问题。

这个系统的主线很简单：

学生提交报修 → 管理员审核 → 管理员派工 → 维修员处理 → 学生确认 → 后勤统计。

整个报告都是围绕“报修工单”展开的。学生提交一次报修，就会产生一张工单；后面的审核、派工、维修、确认和统计，都是在处理这张工单。

## 二、为什么选这个题目

宿舍报修是学校里很常见的管理场景。比如宿舍漏水、灯坏了、门锁坏了、断电了，学生都需要找人维修。

如果只靠电话、微信群或者纸质登记，就容易出现这些问题：

1. 学生报修信息不完整，比如只说“坏了”，但没说宿舍号和具体故障。
2. 学生不知道维修进度，只能反复询问宿管或管理员。
3. 管理员派工靠人工记录，后面不好追踪是谁处理的。
4. 后勤部门想统计哪栋楼维修最多、哪类问题最多，会比较麻烦。

所以这个系统的意义就是把报修流程统一起来，让每一步都有记录、能查询、能统计。

答辩时可以这样说：

> 我选择这个题目，是因为它贴近校园生活，业务流程清楚，而且能完整体现软件工程导论里的需求分析、总体设计、详细设计、编码设计和测试设计。

## 三、系统要达到的目标

这个系统的目标不是简单“提交一个报修”，而是把整个维修流程管起来。

主要目标有五个：

1. 学生可以统一提交报修，填写宿舍号、故障类型、故障描述和附件。
2. 管理员可以审核报修内容，判断是否受理。
3. 管理员可以根据故障类型和维修员工作量进行派工。
4. 维修员可以接收任务，处理后填写维修结果。
5. 后勤部门可以查看统计数据，比如工单数量、故障类型、维修时长等。

简单说，就是让报修流程从“人工沟通”变成“系统记录和管理”。

## 四、为什么采用增量模型

本项目采用的是增量模型。

增量模型可以理解为：先做最核心、最重要的功能，能用起来之后，再慢慢增加其他功能。

对宿舍报修系统来说，最核心的功能是：

1. 学生提交报修。
2. 管理员审核。
3. 管理员派工。
4. 维修员处理。
5. 学生确认。

这些功能先完成后，系统就已经可以跑通主要流程。后面还可以继续加满意度评价、消息提醒、维修材料管理、统计分析等功能。

为什么不用瀑布模型？

瀑布模型要求前期需求非常稳定，一步一步往后做。但宿舍报修系统后期可能会增加新功能，比如移动端提醒、满意度统计，所以增量模型更灵活。

为什么不用螺旋模型？

螺旋模型更适合风险比较高、规模比较大的项目。本项目属于中小型管理信息系统，风险不高，所以不需要那么复杂。

答辩时可以这样说：

> 我选择增量模型，是因为本系统主流程比较明确，可以先完成报修、审核、派工、反馈这些核心功能，再根据实际需求逐步扩展统计、评价和提醒功能。

## 五、需求分析怎么理解

需求分析主要回答三个问题：谁来用系统、系统要做什么、系统要管理哪些数据。

### 5.1 谁来用系统

系统主要有四类用户：

1. 学生  
   学生负责提交报修、查看进度、确认维修结果，也可以对维修服务进行评价。

2. 管理员或宿管  
   管理员负责审核报修内容。如果报修信息真实、完整，就受理；如果信息不完整或不符合要求，就驳回。管理员还负责把工单分配给维修员。

3. 维修员  
   维修员负责接收维修任务，到现场处理故障，然后填写维修结果。

4. 后勤管理部门  
   后勤部门主要看统计数据，比如哪类故障最多、哪些楼栋维修频繁、维修平均耗时是多少。

### 5.2 系统要管理哪些数据

系统中最重要的数据有这些：

1. 学生：包括学号、姓名、宿舍信息。
2. 宿舍：包括楼栋号、房间号、入住学生。
3. 报修工单：包括故障类型、故障描述、图片附件、优先级、状态、提交时间。
4. 派工记录：包括工单编号、维修员、派工时间、处理状态。
5. 维修员：包括维修员编号、姓名、擅长维修类型、当前任务量。
6. 管理员：包括管理员信息和审核记录。

其中最核心的是“报修工单”。只要讲清楚工单，就能讲清楚整个系统。

### 5.3 系统要完成哪些功能

系统功能可以分成五大块：

1. 报修申请管理  
   学生填写报修信息，系统检查信息是否完整，然后生成待审核工单。

2. 工单审核管理  
   管理员检查报修是否有效。有效就通过，无效就驳回。

3. 派工处理管理  
   管理员根据故障类型、紧急程度和维修员负载，把任务分配给合适的维修员。

4. 维修反馈管理  
   维修员完成维修后填写处理结果，学生确认后工单关闭。

5. 统计查询管理  
   后勤部门按工单状态、故障类型、楼栋、维修时长等条件查询和统计。

## 六、总体设计怎么讲

总体设计就是把系统拆成几个主要模块，并说明这些模块之间怎么配合。

本系统可以拆成五个模块：

1. 报修申请模块：接收学生报修信息，生成待审核工单。
2. 工单审核模块：检查报修信息是否真实、完整。
3. 派工处理模块：选择维修员，生成派工记录。
4. 维修反馈模块：记录维修结果，更新工单状态。
5. 统计查询模块：读取工单和维修记录，生成统计结果。

模块之间的关系可以这样理解：

学生提交报修后，报修申请模块生成工单；工单进入审核模块；审核通过后进入派工模块；派工后维修员处理；维修完成后学生确认；最后这些数据会进入统计查询模块。

答辩时重点说：

> 我的总体设计是以报修工单为中心，把系统按业务流程拆成五个模块。每个模块只负责一个阶段，这样结构比较清楚，也方便后续维护和扩展。

## 七、详细设计怎么讲

详细设计就是从系统模块中选出比较关键的模块，把内部处理步骤说清楚。

报告里选择了两个模块：

1. 报修申请受理模块。
2. 派工处理模块。

### 7.1 报修申请受理模块

这个模块是系统入口，学生提交报修时首先会经过它。

它的处理步骤是：

1. 学生填写学号、宿舍号、故障类型、故障描述和附件。
2. 系统先检查必填项有没有为空。
3. 系统查询学生宿舍档案，判断学生和宿舍是否匹配。
4. 系统检查附件格式、大小和数量是否符合要求。
5. 系统根据故障类型判断是否属于紧急故障。
6. 系统生成报修工单，并通知管理员审核。

为什么选这个模块做详细设计？

因为它包含顺序、判断和循环三种常见程序结构。比如必填项检查是判断，附件检查是循环，生成工单是顺序处理。所以它适合用程序流程图和 PDL 伪代码来表达。

### 7.2 派工处理模块

派工处理模块负责把工单分给合适的维修员。

它的处理步骤是：

1. 系统读取待派工的工单。
2. 按紧急程度排序，紧急工单优先处理。
3. 对每一张工单逐个处理。
4. 根据故障类型筛选合适维修员。
5. 如果没有合适维修员，工单进入待协调状态。
6. 如果有合适维修员，就选择当前任务量最少的维修员。
7. 系统生成派工记录，并通知维修员。

这个模块的重点是派工规则。不是随便派一个人，而是既要看维修员会不会修这个类型的故障，也要看他当前任务多不多。

### 8.1 UML 类图

类图主要说明系统里有哪些对象，以及这些对象之间有什么关系。

本项目里的主要类有学生、宿舍、报修工单、派工记录、维修员、管理员等。

学生住在宿舍里，学生可以提交报修工单；管理员审核工单并进行派工；维修员根据派工记录处理工单；工单最后会形成维修结果和统计数据。

顶层 DFD 是从最外层看系统。

它把整个系统看成一个整体，重点说明系统和外部用户之间传递了哪些数据。

比如学生向系统提交报修信息，系统向学生返回工单状态；管理员向系统提交审核和派工信息；维修员提交维修反馈；后勤部门从系统获取统计结果。

### 8.3 0 层 DFD

0 层 DFD 是把顶层 DFD 展开，进一步说明系统内部有哪些主要处理过程。

本项目的 0 层 DFD 包括：

1. 报修申请。
2. 工单审核。
3. 派工处理。
4. 维修反馈。
5. 统计查询。

这些处理过程也正好对应总体设计中的五个主要模块。

### 8.4 状态图

状态图说明一张报修工单从创建到结束会经历哪些状态。

工单的状态大致包括：

待提交 → 待审核 → 待派工 → 处理中 → 待确认 → 已完成。

如果审核不通过，也可能进入“已驳回”状态。

这个图的作用是让工单流程更清楚，避免出现状态混乱，比如还没审核就直接维修，或者维修完成后没有确认。

### 8.5 系统结构图

系统结构图说明系统模块之间的层次关系。

它和 0 层 DFD 的关系是：0 层 DFD 里的主要加工，可以转换成系统结构图里的功能模块。

它展示了从学生提交信息，到系统校验、判断、生成工单、通知管理员的完整过程。

### 8.8 用例图

## 九、PDL 伪代码怎么讲

报告里的 PDL 伪代码写的是“报修申请受理模块”。

它大概做了这些事情：

1. 如果学号、宿舍号、故障类型或故障描述为空，就返回提交失败。
2. 查询学生宿舍档案，如果学生和宿舍不匹配，就返回失败。
3. 逐个检查附件，如果格式或大小不符合要求，就返回失败。
4. 如果附件数量超过限制，也返回失败。
5. 如果故障类型是漏水、断电、门锁损坏，就设置为高优先级。
6. 否则设置为普通优先级。
7. 最后生成工单，并通知管理员。

答辩时可以强调：

> 我选择这个模块写伪代码，是因为它既有输入校验，又有分支判断和循环检查，能比较完整地体现程序逻辑。

## 十、测试设计怎么讲

测试部分主要针对报修申请受理模块。

为什么测这个模块？

因为它是系统入口，用户输入最多，也最容易出错。如果入口校验不严格，后面的审核、派工和统计都会受影响。

### 10.1 白盒测试

白盒测试是从程序内部逻辑出发，看程序里的每条语句、每个判断、每条路径有没有被覆盖。

本项目设计了：

1. 语句覆盖：让主要语句至少执行一次。
2. 判定-条件覆盖：让每个关键判断的真和假都出现。
3. 条件组合覆盖：测试多个条件组合在一起时的情况。
4. 独立路径覆盖：覆盖信息不完整、档案不匹配、附件不合法、附件数量超限、紧急故障成功、普通故障成功等路径。

### 10.2 黑盒测试

黑盒测试不看程序内部怎么写，只看输入和输出是否符合需求。

本项目用了两种方法：

1. 等价类划分  
   比如学生号可以分成有效学生号、空学生号、不存在学生号；附件可以分成合法图片、非法格式、大小超限等。

2. 边界值分析  
   比如故障描述要求 5 到 200 字，就要测试 5 字、200 字、4 字、201 字；附件数量允许 0 到 5 个，就要测试 0 个、5 个、6 个。

答辩时可以这样说：

> 白盒测试主要验证程序内部逻辑，黑盒测试主要验证用户输入和系统输出。两个角度结合起来，可以更全面地检查报修申请受理模块。

## 十二、预期答辩问题与参考回答

### 问题 1：为什么选择宿舍报修管理系统？

参考回答：因为宿舍报修和校园生活联系紧密，业务流程也比较清楚。它包含提交申请、审核、派工、处理、确认和统计等环节，能比较完整地体现软件工程课程中的分析和设计过程。

### 问题 2：这个系统最核心的对象是什么？

参考回答：最核心的是报修工单。学生提交报修后生成工单，管理员审核工单，维修员根据工单处理任务，学生确认后关闭工单，后勤部门也根据工单数据进行统计。

### 问题 3：为什么使用增量模型？

参考回答：因为系统可以先完成核心流程，比如报修、审核、派工、维修反馈，然后再增加评价、提醒、统计等功能。这样更灵活，也更符合中小型管理系统的开发特点。

### 问题 4：如果用瀑布模型行不行？

参考回答：也可以，但不如增量模型灵活。瀑布模型适合需求非常固定的项目，而宿舍报修系统后续可能会扩展新功能，所以增量模型更合适。

### 问题 5：系统有哪些用户？

参考回答：主要有学生、管理员或宿管、维修员和后勤管理部门。学生提交报修，管理员审核派工，维修员处理维修，后勤部门查看统计数据。

### 问题 6：系统有哪些主要模块？

参考回答：主要有报修申请模块、工单审核模块、派工处理模块、维修反馈模块和统计查询模块。这些模块按业务流程依次衔接。

### 问题 7：DFD 和系统结构图有什么关系？

参考回答：DFD 主要说明数据怎么流动，系统结构图主要说明功能模块怎么划分。0 层 DFD 里的报修申请、工单审核、派工处理、维修反馈和统计查询，可以转换成系统结构图里的五个主要模块。

### 问题 8：为什么选报修申请受理模块做详细设计？

参考回答：因为它是系统入口，用户输入多，判断条件多，还要循环检查附件。它包含顺序、分支和循环结构，适合用流程图和伪代码表示。

### 问题 9：为什么选派工处理模块做 N-S 图？

参考回答：因为派工处理模块逻辑比较典型，要循环处理待派工工单，还要判断有没有合适维修员。N-S 图适合表示这种结构化的循环和判断逻辑。

### 问题 10：工单有哪些状态？

参考回答：主要有待提交、待审核、已驳回、待派工、处理中、待确认和已完成。每个状态都对应业务流程中的一个阶段。

### 问题 11：系统怎么判断紧急程度？

参考回答：根据故障类型判断。比如漏水、断电、门锁损坏这类影响生活或安全的问题，设置为高优先级；普通灯管损坏等问题可以设置为普通优先级。

### 问题 12：派工时怎么选择维修员？

参考回答：先看维修员是否擅长处理这种故障，再看维修员当前任务量。系统优先选择符合故障类型并且负载较低的维修员。

### 问题 13：为什么测试报修申请受理模块？

参考回答：因为这个模块是系统入口，输入情况最复杂，最容易出现错误。如果这里校验不严格，后面的审核、派工和统计都会受到影响。

### 问题 14：白盒测试测什么？

参考回答：白盒测试主要看程序内部逻辑，比如语句有没有执行到，判断条件的真假有没有覆盖，主要路径有没有测试到。

### 问题 15：黑盒测试测什么？

参考回答：黑盒测试主要看输入和输出是否正确，不关心内部代码怎么写。比如输入空学号、错误宿舍号、非法附件时，系统应该给出对应提示。

### 问题 16：等价类划分是什么意思？

参考回答：等价类划分就是把输入分成几类，每类选代表数据测试。比如学生号可以分成有效学生号、空学生号和不存在的学生号。

### 问题 17：边界值分析是什么意思？

参考回答：边界值分析就是重点测试临界点附近的数据。比如故障描述要求 5 到 200 字，就要测试 4 字、5 字、200 字、201 字。

### 问题 18：怎样保证前后设计一致？

参考回答：报告一直围绕报修工单展开。类图描述工单相关对象，DFD 描述工单数据流，状态图描述工单状态变化，详细设计、伪代码和测试也都围绕报修申请受理模块展开，所以整体是统一的。

### 问题 19：系统后续还能扩展什么？

参考回答：可以扩展移动端提醒、满意度评价、维修材料管理、维修员绩效统计、超时预警和常见故障知识库等功能。

### 问题 20：这个项目体现了哪些软件工程知识？

参考回答：体现了开发模型选择、需求分析、结构化分析、模块化设计、详细设计、伪代码表达和软件测试设计，也用到了 UML 类图、DFD、状态图、结构图、流程图、N-S 图和用例图。

## 十三、答辩时要注意什么

1. 不要只说“这是一个报修系统”，要说它是按软件工程流程完成的分析与设计项目。
2. 多围绕“报修工单”讲，因为它贯穿整个系统。
3. 讲增量模型时，重点说“先做核心流程，再扩展其他功能”。
4. 讲 DFD 和结构图时，说明 DFD 的加工可以转换成系统模块。
5. 讲测试时，说明白盒测试看内部逻辑，黑盒测试看输入输出。
6. 老师问扩展功能时，可以说消息提醒、满意度评价、材料管理和统计分析。

## 十四、超短总结

本项目是一个宿舍报修管理系统的分析与设计。系统以报修工单为核心，把学生报修、管理员审核派工、维修员处理、学生确认和后勤统计串成完整流程。项目采用增量模型，完成了需求分析、总体设计、详细设计、PDL 伪代码和测试设计，能够较完整地体现软件工程导论课程的主要知识点。
