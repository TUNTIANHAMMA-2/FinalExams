# 宿舍报修管理系统答辩准备说明

## 一、项目概述

本项目的题目是“宿舍报修管理系统分析与设计”，属于《软件工程导论》期末考查项目。项目面向高校宿舍日常维修管理场景，重点解决学生报修渠道分散、维修进度不透明、维修派工缺少记录、后勤统计依赖人工整理等问题。

系统以“报修工单”为核心业务对象，围绕学生、管理员、维修员和后勤管理部门四类参与者，形成“学生提交报修、管理员审核派工、维修员处理反馈、学生确认评价、后勤统计分析”的完整业务闭环。

本项目不是单纯写一个程序，而是按照软件工程方法完成一个中小型管理信息系统的需求分析、总体设计、详细设计、伪代码设计和软件测试设计。因此，报告重点体现的是软件开发前期分析与设计能力。

## 二、选题背景与意义

高校宿舍维修是比较典型的事务管理场景。传统处理方式通常依赖电话、微信群、纸质登记表或人工通知，容易出现以下问题：

1. 学生报修信息不统一，容易漏填宿舍号、故障类型和故障描述。
2. 管理员派工过程不透明，学生难以及时了解维修进度。
3. 维修员任务记录分散，不便于统计工作量和处理时长。
4. 后勤部门需要人工汇总维修数据，效率低且容易出错。

设计宿舍报修管理系统后，可以把报修、审核、派工、处理、确认和统计流程统一到系统中，提高维修处理效率，也方便后勤部门进行数据查询和管理决策。

## 三、系统目标

本系统的总体目标是建立一个规范化、可追踪、可统计的宿舍维修管理流程。

具体目标包括：

1. 为学生提供统一的报修入口，规范报修信息填写。
2. 为管理员提供工单审核和派工功能，提高派工效率。
3. 为维修员提供任务接收和维修反馈功能，保证维修过程有记录。
4. 为学生提供进度查询和结果确认功能，提高维修过程透明度。
5. 为后勤部门提供统计查询功能，支持按状态、类型、楼栋、维修时长等维度分析。

## 四、开发模型选择

本项目采用增量模型。

选择增量模型的原因是：宿舍报修系统的核心业务流程比较清晰，可以先完成最重要的报修、审核、派工和反馈主流程，然后根据实际使用反馈逐步扩展统计分析、满意度评价、移动端提醒、维修材料管理等功能。

与瀑布模型相比，增量模型更灵活，可以分阶段交付和调整；与螺旋模型相比，本系统规模较小、风险较低，不需要投入过多的风险分析成本。因此，增量模型更适合本项目。

本项目可以划分为以下增量：

1. 第一增量：完成学生报修、管理员审核和基本工单管理。
2. 第二增量：完成派工处理、维修员反馈和学生确认。
3. 第三增量：完成统计查询、评价管理和数据导出。
4. 后续增量：扩展移动端消息提醒、维修材料库存管理、满意度分析等功能。

## 五、需求分析

### 5.1 参与者

系统主要参与者包括：

1. 学生：提交报修申请、查询维修进度、确认维修结果、评价维修服务。
2. 管理员或宿管：审核报修信息、驳回无效申请、根据故障类型和维修员负载进行派工。
3. 维修员：接收维修任务、处理故障、填写维修结果。
4. 后勤管理部门：查询维修数据、查看统计报表、分析宿舍维修情况。

### 5.2 核心数据对象

系统涉及的主要数据对象包括：

1. 学生：保存学生编号、姓名、所属宿舍等信息。
2. 宿舍：保存楼栋号、房间号、入住学生等信息。
3. 报修工单：保存故障类型、故障描述、附件、优先级、状态和提交时间等信息。
4. 派工记录：保存工单、维修员、派工时间和派工状态等信息。
5. 维修员：保存维修员编号、姓名、擅长类型和当前负载等信息。
6. 管理员：保存管理员编号、姓名和审核操作记录等信息。

其中，“报修工单”是系统最核心的数据对象，因为从报修提交到最终关闭，整个业务流程都是围绕工单状态变化展开的。

### 5.3 核心功能

系统核心功能可以分为五类：

1. 报修申请管理：学生填写宿舍号、故障类型、故障描述和附件，系统校验信息后生成工单。
2. 工单审核管理：管理员检查报修信息是否真实、完整，决定受理或驳回。
3. 派工处理管理：管理员根据故障类型、紧急程度和维修员负载选择维修员。
4. 维修反馈管理：维修员完成维修后填写处理结果，学生确认后关闭工单。
5. 统计查询管理：后勤部门按工单状态、故障类型、楼栋宿舍、维修时长等条件查询和导出统计结果。

## 六、总体设计

### 6.1 系统模块划分

根据 0 层 DFD 的主要加工，系统可以划分为以下模块：

1. 报修申请模块：负责接收学生报修信息，完成基础校验并生成待审核工单。
2. 工单审核模块：负责读取学生和宿舍档案，判断报修申请是否有效。
3. 派工处理模块：负责根据工单信息和维修员信息生成派工记录。
4. 维修反馈模块：负责维修员填写处理结果、学生确认维修完成并更新工单状态。
5. 统计查询模块：负责读取工单库和维修记录，生成统计报表。

这些模块之间通过工单状态和数据存储进行衔接。报修申请模块输出待审核工单，审核模块输出有效工单或驳回结果，派工模块输出派工记录，维修反馈模块更新维修结果和工单状态，统计查询模块读取历史数据生成报表。

### 6.2 总体设计特点

系统总体设计的特点有三点：

1. 以工单为中心：所有业务操作最终都落到报修工单的创建、审核、派工、处理和关闭。
2. 模块职责清晰：每个模块只处理一个阶段的核心任务，便于维护和扩展。
3. 数据流一致：DFD、系统结构图、状态图和测试设计都围绕同一条主业务流程展开，保证前后设计一致。

## 七、详细设计

### 7.1 报修申请受理模块

详细设计中选择的第一个模块是“报修申请受理模块”。该模块使用程序流程图描述，原因是它包含明显的顺序、分支和循环逻辑，适合用流程图展示。

该模块的主要处理过程是：

1. 学生输入学号、宿舍号、故障类型、故障描述和附件。
2. 系统检查必填信息是否完整。
3. 系统查询学生宿舍档案，判断学生和宿舍是否匹配。
4. 系统循环检查附件格式、大小和数量。
5. 系统根据故障类型判断紧急程度。
6. 系统生成报修工单并通知管理员。

该模块体现了输入校验、档案匹配、循环检查和条件判断，是后续伪代码和测试设计的主要对象。

### 7.2 派工处理模块

详细设计中选择的第二个模块是“派工处理模块”。该模块使用 N-S 图描述，原因是 N-S 图适合表示结构化程序设计中的顺序、选择和循环结构。

该模块的主要处理过程是：

1. 系统读取待派工工单。
2. 按紧急程度对工单排序。
3. 对每一张待派工工单进行循环处理。
4. 根据故障类型筛选合适维修员。
5. 如果没有可派维修员，则将工单置为待协调状态。
6. 如果存在可派维修员，则选择当前负载最低的维修员。
7. 系统生成派工记录，并通知维修员。

该模块的设计重点是派工规则：既要考虑故障类型是否匹配，也要考虑维修员当前负载，避免任务分配不均。

## 九、伪代码设计说明

报告中的 PDL 伪代码选择“报修申请受理模块”作为编码对象。

伪代码的核心逻辑包括：

1. 判断学生号、宿舍号、故障类型和故障描述是否为空。
2. 查询学生宿舍档案，判断学生与宿舍是否匹配。
3. 循环检查附件类型和附件大小。
4. 判断附件数量是否超过限制。
5. 根据故障类型设置工单优先级。
6. 生成报修工单。
7. 通知管理员审核。

选择该模块编写伪代码的原因是：该模块既有输入校验，又有分支判断和循环结构，能够体现程序设计的完整性，也便于后续设计白盒测试和黑盒测试。

## 十、测试设计说明

### 10.1 白盒测试

白盒测试从程序内部逻辑出发，针对 PDL 伪代码设计测试用例。

报告中设计了以下覆盖方式：

1. 语句覆盖：保证主要语句至少执行一次。
2. 判定-条件覆盖：保证关键判断条件的真假结果都被覆盖。
3. 条件组合覆盖：覆盖多个条件组合下的有效和无效情况。
4. 独立路径覆盖：覆盖信息不完整、档案不匹配、附件非法、附件数量超限、紧急故障成功、普通故障成功等主要路径。

### 10.2 黑盒测试

黑盒测试从用户输入角度出发，不关心程序内部实现，只关注输入和输出是否符合需求。

报告中使用了两种方法：

1. 等价类划分：把学生号、宿舍号、故障类型、故障描述和附件划分为有效等价类与无效等价类。
2. 边界值分析：重点测试故障描述长度、附件数量、附件大小和宿舍号格式等边界情况。

选择报修申请受理模块作为测试对象，是因为该模块位于系统入口，输入情况复杂，错误输入较多，测试价值较高。

## 十二、预期答辩问题与参考回答

### 问题 1：为什么选择宿舍报修管理系统作为题目？

参考回答：宿舍报修管理系统贴近校园生活，业务流程清晰，包含用户提交、管理员审核、任务分配、处理反馈和统计查询等典型管理信息系统功能，适合用于展示软件工程导论中的需求分析、总体设计、详细设计和测试设计方法。

### 问题 2：这个系统的核心业务对象是什么？

参考回答：核心业务对象是报修工单。学生提交报修后生成工单，管理员审核工单，维修员根据工单处理任务，学生确认后关闭工单，后勤部门也基于工单数据进行统计分析。

### 问题 3：为什么选择增量模型？

参考回答：因为本系统核心流程明确，但后续功能可以逐步扩展。可以先实现报修、审核、派工和反馈主流程，再扩展统计分析、满意度评价、移动端提醒等功能。增量模型适合分阶段交付，也便于根据用户反馈调整。

### 问题 4：如果使用瀑布模型可以吗？

参考回答：可以，但不是最优选择。瀑布模型适合需求非常稳定的项目，而宿舍报修系统虽然主流程清楚，但后续可能增加评价、提醒、材料管理等功能，所以使用增量模型更灵活。

### 问题 5：系统有哪些参与者？

参考回答：主要有学生、管理员或宿管、维修员和后勤管理部门。学生负责提交报修和确认结果，管理员负责审核和派工，维修员负责处理维修任务，后勤部门负责统计查询和管理分析。

### 问题 6：系统有哪些主要功能模块？

参考回答：主要包括报修申请模块、工单审核模块、派工处理模块、维修反馈模块和统计查询模块。这些模块对应从报修提交到统计分析的完整流程。

### 问题 7：DFD 和系统结构图之间有什么关系？

参考回答：0 层 DFD 描述系统的数据流和主要加工，系统结构图则根据这些加工转换成功能模块。比如 0 层 DFD 中的报修申请、工单审核、派工处理、维修反馈和统计查询，分别对应系统结构图中的一级功能模块。

### 问题 8：为什么详细设计选择报修申请受理模块？

参考回答：因为报修申请受理模块是系统入口，涉及必填项校验、学生宿舍档案匹配、附件循环检查、紧急程度判断等逻辑，包含顺序、分支和循环结构，适合用流程图和 PDL 伪代码进行详细设计。

### 问题 9：为什么详细设计选择派工处理模块？

参考回答：派工处理模块体现了系统的核心管理逻辑，需要根据故障类型和维修员负载进行任务分配，同时还要处理没有可用维修员的情况，因此适合用 N-S 图展示结构化逻辑。

### 问题 10：报修工单有哪些状态？

参考回答：主要包括待提交、待审核、已驳回、待派工、处理中、待确认和已完成等状态。状态变化由提交、审核通过、驳回、派工、维修完成和学生确认等事件触发。

### 问题 11：系统如何判断工单优先级？

参考回答：系统根据故障类型判断优先级。例如漏水、断电、门锁损坏等影响安全或正常生活的故障设置为高优先级，普通灯管损坏等设置为普通优先级。

### 问题 12：派工时如何选择维修员？

参考回答：先根据故障类型筛选具备对应维修能力的维修员，再从候选维修员中选择当前负载最低的人。如果没有可用维修员，则工单进入待协调状态。

### 问题 13：为什么测试对象选择报修申请受理模块？

参考回答：因为该模块是用户输入入口，输入情况复杂，容易出现空值、格式错误、附件非法、档案不匹配等问题。同时该模块包含分支和循环逻辑，适合同时进行白盒测试和黑盒测试。

### 问题 14：白盒测试设计了哪些覆盖？

参考回答：设计了语句覆盖、判定-条件覆盖、条件组合覆盖和独立路径覆盖。这样可以从程序内部逻辑角度验证主要语句、判断条件、组合条件和关键路径。

### 问题 15：黑盒测试使用了哪些方法？

参考回答：主要使用等价类划分和边界值分析。等价类划分用于测试学生号、宿舍号、故障类型、故障描述和附件的有效与无效输入；边界值分析用于测试描述长度、附件数量、附件大小等边界情况。

### 问题 16：如何保证报告前后一致？

参考回答：报告中所有内容都围绕报修工单和报修处理流程展开。类图描述核心对象，DFD 描述数据流，状态图描述工单状态变化，结构图由 DFD 转换而来，详细设计、伪代码和测试都选择报修申请受理模块作为重点，因此前后保持一致。

### 问题 17：这个系统后续可以扩展哪些功能？

参考回答：可以扩展移动端消息提醒、维修材料库存管理、维修满意度统计、维修员绩效分析、超时预警、常见故障知识库等功能。

### 问题 18：如果学生提交错误信息怎么办？

参考回答：系统会先进行必填项校验和宿舍档案匹配。如果信息不完整或学生与宿舍不匹配，会拒绝提交或提示修改。管理员审核阶段也可以驳回不真实或描述不清的报修申请。

### 问题 19：如果维修员完成维修但学生不确认怎么办？

参考回答：可以设置超时确认机制。例如维修员提交完成后，系统进入待确认状态；如果学生在规定时间内没有反馈，系统可以提醒学生，或者由管理员核实后关闭工单。

### 问题 20：这个项目体现了哪些软件工程思想？

参考回答：项目体现了生命周期模型选择、需求分析、结构化分析、模块化设计、详细设计、伪代码表达和软件测试设计等思想。通过 UML、DFD、状态图、结构图、流程图、N-S 图和测试用例，把一个实际业务场景转化为规范的软件设计文档。

## 十三、答辩时的重点提醒

1. 不要只说“这是一个报修系统”，要强调它是按照软件工程流程完成的分析与设计项目。
2. 重点围绕“报修工单”讲，因为工单贯穿需求、设计、状态、伪代码和测试。
3. 解释增量模型时，要说明“先交付核心流程，再逐步扩展功能”。
4. 解释 DFD 和结构图时，要说明二者之间的转换关系。
5. 解释测试时，要说清楚白盒测试看内部逻辑，黑盒测试看输入输出。
6. 如果老师追问后续改进，可以回答移动端提醒、满意度评价、材料管理和统计分析。

## 十四、简短版总结

本项目是一个面向高校宿舍维修场景的管理信息系统分析与设计项目。系统以报修工单为核心，完成学生报修、管理员审核派工、维修员处理反馈、学生确认和后勤统计的完整流程。项目采用增量模型，按照软件工程方法完成需求分析、总体设计、详细设计、PDL 伪代码和测试设计，并使用多种图表保证设计表达清晰、前后一致。
