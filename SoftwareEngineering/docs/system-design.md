# 系统设计说明

## 1. 总体设计主线

系统围绕“报修工单”展开。学生提交报修后，工单在系统中经历审核、派工、维修、反馈、确认和归档等状态。管理员、维修员和后勤部门围绕工单进行协作。

整体链路可以概括为：

```text
学生提交报修
-> 系统校验宿舍和故障信息
-> 管理员审核
-> 管理员派工
-> 维修员处理
-> 学生确认评价
-> 后勤统计分析
```

## 2. 需求分析

### 2.1 功能需求

| 模块 | 功能 |
| --- | --- |
| 报修申请管理 | 填写报修信息、上传附件、提交申请、查看状态 |
| 工单审核派工 | 审核报修内容、判断紧急程度、分配维修员 |
| 维修处理反馈 | 接收任务、记录处理过程、上传处理结果 |
| 确认评价 | 学生确认维修结果并评价 |
| 统计查询 | 按宿舍、故障类型、维修员、时间范围统计 |

### 2.2 非功能需求

- 信息完整性：报修必须包含学生、宿舍、故障类型和故障描述。
- 可追踪性：工单状态变化和派工记录需要保留。
- 易用性：学生提交报修流程应简洁。
- 可统计性：后勤能够按多维度查询维修情况。

## 3. 数据对象设计

核心对象包括：

- `学生`：学号、姓名、联系方式、宿舍号。
- `宿舍`：楼栋、房间号、床位、所属院系。
- `报修工单`：工单号、故障类型、描述、状态、紧急程度、提交时间。
- `派工记录`：派工人、维修员、派工时间、任务说明。
- `维修员`：编号、姓名、工种、联系方式。
- `管理员`：编号、姓名、权限范围。
- `评价记录`：满意度、评价内容、确认时间。

这些对象共同支撑类图、数据字典和工单状态图。

## 4. 数据流设计

顶层 DFD 用于描述系统边界：

- 外部实体：学生、管理员、维修员、后勤管理部门。
- 核心系统：宿舍报修管理系统。
- 数据存储：学生档案、宿舍档案、报修工单、派工记录、维修反馈、统计报表。

0 层 DFD 将系统拆为主要加工：

1. 报修申请受理。
2. 工单审核。
3. 派工处理。
4. 维修反馈确认。
5. 统计查询。

## 5. 总体结构设计

系统结构图由 0 层 DFD 转换而来：

```text
宿舍报修管理系统
```

## 6. 详细设计

报告重点选择两个模块：

| 模块 | 表达方式 | 选择原因 |
| --- | --- | --- |
| 报修申请受理 | 程序流程图、PDL 伪代码 | 包含输入校验、宿舍匹配、附件检查、紧急程度判断 |
| 派工处理 | N-S 图 | 体现审核后按工种、区域和负载选择维修员 |

报修申请受理模块适合展示顺序、分支和循环结构，因此也适合作为测试设计对象。

## 7. 测试设计

白盒测试：

- 语句覆盖：保证主要处理语句至少执行一次。
- 判定-条件覆盖：覆盖必填项、宿舍匹配、附件合法性和紧急故障判断。
- 条件组合覆盖：组合不同输入条件验证路径。
- 独立路径覆盖：覆盖核心控制流路径。

黑盒测试：

- 等价类划分：有效报修、缺失字段、无效宿舍、非法附件等。
- 边界值分析：描述长度、附件数量、联系方式长度等边界。

## 8. 设计一致性

报告中的设计应保持同一主线：

- 类图中的核心类对应数据字典。
- DFD 中的数据存储对应类图中的主要对象。
- 结构图的模块来自 0 层 DFD 的加工。
- PDL 和测试用例围绕同一个报修申请受理模块。

答辩时强调这种一致性，比单独解释某一张图更重要。
